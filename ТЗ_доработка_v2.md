## 0. Важное замечание о предыдущем ТЗ (v1.0)

Предыдущее ТЗ содержало ряд утверждений, которые **противоречат фактическому состоянию кода**. Ниже перечень поправок, которые учтены в новом ТЗ:

| Пункт | Что было заявлено | Что на самом деле / как исправлено |
|---|---|---|
| §3.1 Создание подпапок | «нет возможности выбрать родителя» | `createFolder(name, parent?)` в сторе **уже принимает `parent`**; тип `Folder` уже имеет `parent`/`children`. Не хватает только **UI-селектора родителя** в `FolderModal` + каскадного обновления ссылок в `renameFolder`/`deleteFolder`. Поправлено в §3.1–3.4 |
| §3.4 Иконки и цвета | «поля `icon`/`color` не применяются в интерфейсе» | **НЕВЕРНО.** Иконки и цвета **применяются** в Sidebar (`folderIcon()`, `folder.color`). Реальная проблема: в `FolderModal` кнопки выбора иконки/цвета — **мёртвый UI без `onClick`**, и данными они не сохраняются. Поправлено в §3.4 |
| §3.2 Перемещение папок | «нет кнопок перемещения» | ВЕРНО. Методов `moveFolderUp/Down` нет. Поле `order` есть, но не читается при сортировке (подтверждено в §7.1) |
| §4.1 System/Context/Output | добавление полей `system/context/output/useTemplate` | Типа `Prompt` с такими полями нет — только единый `content`. Предложение валидно, но требует аккуратной миграции (`content`, seed, импорт/экспорт, шаблонные переменные). Переработано в §4 |
| §5.1 Объединение при импорте | «проверяется только существование по названию/пути» | На деле **конфликт-диалога нет вообще** — при импорте `.prmt` промпты просто добавляются в начало массива с новыми id, без проверки дубликатов. Поправлено в §5 |
| §7.2 Ctrl+Shift+C | «есть отдельная кнопка» | **НЕВЕРНО.** Подстановка переменных (`handleCopy(true)`) **недостижима**: её не вызывает ни кнопка, ни хоткей. Заявленный в ShortcutsModal `⌘⇧C` не реализован. Поправлено в §7.2 |
| §6 Electron | — | В проект **нет Electron вообще** (ни в deps, ни main-процесса, ни preload). Формат «в перспективе Electron» верен. См. §6 |

**Новые/упущенные пункты, добавленные в ТЗ** (их не было в v1.0):
- Полное несоответствие заявленных хоткеев реализованным: работают только `⌘K`, `⌘S`, `Esc` (в модалках); `⌘N`, `⌘F`, `⌘C`, `⌘⇧C`, `F2` — **отсутствуют**.
- Баг: пункт навигации «По тегам» вызывает **`openShortcuts()`** (открывает окно горячих клавиш вместо просмотра по тегам).
- Осиротевший флаг `tagModalOpen` (нет методов open/close и компонента).
- Переименование папки (`renameFolder`) реализовано в сторе, но **недостижимо из UI**.
- Поиск иконок по имени (`folderIcon`) **ломается после переименования папки** (нет стабильного id).
- `deleteFolder` не каскадит удаление дочерних папок и не предупреждает о числе затрагиваемых промптов.
- Настройки «Автосохранение / Шрифт / Формат» и «Расположение данных» в Settings — **нерабочие заглушки**.
- XSS-риск в `renderMarkdown` (неэкранированный `href` в ссылках → `javascript:` и «выбивание» атрибута) при использовании `dangerouslySetInnerHTML`.
- Коллизия id: `createPrompt`/`duplicatePrompt` используют `Date.now()`.
- Мёртвый код: интерфейсы `Theme`, `ExportData`, функция `formatDate`, no-op `createTag`, неиспользуемые `addVar`/`removeVar`/`toggleSidebar`/`updateCustomTheme`; дубль интерфейса `CustomTheme`.

## 2. Общие требования к доработке

### 2.1. Основные принципы
- **Сохранение существующей архитектуры.** Все изменения вписываются в текущую структуру: `stores` (Zustand), `components` (в рамках `App.tsx` до шага рефакторинга §10, затем — в `src/components/`), `utils`, `shared/types`.
- **Обратная совместимость.** Доработки не должны ломать существующий функционал; при изменении схем данных (`Prompt`, `ExportData`) обеспечить миграцию существующих `localStorage`-данных.
- **Код-стайл.** Соблюдать строгую типизацию TypeScript (`strict`, `noUnusedLocals/Params`), функциональные компоненты, Zustand для состояния. Без магии.
- **Дизайн-система.** Новые элементы используют CSS-переменные токены (`--bg-panel`, `--text-primary`, `--border-primary`, `--accent-primary`, `--shadow-*`, радиусы/анимации) и утилиту `cn()`. Не хардкодить цвета/отступы.
- **Тестирование.** После каждой доработки — проверка всей системы (см. §9).
- **ARIA/доступность.** Новые интерактивные элементы получают корректные `aria-label`, `role`, фокус-кольца (стандарт проекта — `:focus-visible` с `--shadow-glow`).

### 2.2. Обязательный аудит перед началом (день 1, до фич)
1. `npm install` (в репозитории нет `node_modules`).
2. `npx tsc --noEmit` — убедиться, что код проходит типизацию (проект strict).
3. `npm run build` — убедиться, что собирается единый `index.html`.
4. Поднять `npm run dev` — вручную проверить работающий функционал (CRUD промпта, папки, темы, экспорт, поиск, копирование).

## 3. Доработка управления папками

> Факт: тип `Folder` уже содержит `name, parent: string|null, children: string[], icon?, color?, order`. В сторе есть `createFolder` (принимает `parent`, но ставит хардкод `icon:'Folder'`, `color:'#FF6B35'`), `renameFolder`, `deleteFolder`. **Не хватает**: UI-выбора родителя, каскадного обновления ссылок, методов перемещения, контекстного меню, рабочего выбора иконки/цвета.

### 3.1. Создание подпапок (выбор родителя)
- **Где:** `FolderModal` (`App.tsx`, ~строка 1786).
- Требование: при создании папки — выпадающий список выбора родительской папки (root-опция «Корневая папка» + все существующие папки).
- Реализация:
  1. В `FolderModal` добавить состояние `parentFolder: string | null` (по умолчанию `null`).
  2. Рендерить `<select>` со всеми папками; значение передавать в `createFolder(name, parentFolder)`.
  3. Доработать стор `createFolder`:
     - обновлять `children` у родителя;
     - допускать иерархию произвольной глубины (рекурсивно не ограничивать).
- **Доработка каскада (обязательно, иначе иерархия «сломана»):**
  - `renameFolder(oldName, newName)` — обновлять `parent` и `children` всех папок, ссылающихся на старую папку (сейчас обновляются только `prompts[].folder/path` и `selectedFolder`).
  - `deleteFolder(name)` — каскадно удалять все дочерние папки (рекурсивно по `children`) и их промпты; до удаления возвращать число затрагиваемых промптов для подтверждения.

### 3.2. Перемещение папок вверх/вниз
- **Где:** store + `Sidebar` (item-actions папки).
- Требование: кнопки «Вверх» ▲ и «Вниз» ▼ в item-actions каждой папки (hover-блок рядом с кнопкой удаления).
- Реализация в сторе (методов сейчас нет):
  - `moveFolderUp(name: string)` и `moveFolderDown(name: string)`.
  - Перемещение только **среди сиблингов** (папок с тем же `parent`): находим отсортированную по `order` группу сиблингов, меняем местами значения `order` с соседом. Если папка уже первая/последняя — no-op (или toast-info).
  - Идемпотентно и атомарно (без гонок в `set`).
- **UI:** две кнопки-иконки (ArrowUp/ArrowDown) в item-actions, `title="Переместить вверх/вниз"`, `stopPropagation`.

### 3.3. Контекстное меню для папок
- Требование: правый клик на nav-item папки открывает контекстное меню со следующими действиями:
  1. Переименовать (открыть модалку переименования — см. §3.5)
  2. Создать подпапку (открыть `FolderModal` с предвыбранным родителем = этой папкой)
  3. Переместить вверх
  4. Переместить вниз
  5. Создать промпт в этой папке
  6. Удалить папку (с подтверждением, учитывая дочерние и промпты)
- Реализация:
  - Компонент `FolderContextMenu` (позиционируемый по `x/y`, отрисовка через `createPortal` в `document.body`).
  - Обработчик `onContextMenu` на каждом nav-item папки (`e.preventDefault()`, запомнить координаты и папку).
  - Закрытие: клик вне меню, `Escape`, перенос в другой элемент.
  - Стили: `--bg-elevated`, `--border-primary`, `--shadow-lg`; пункт «Удалить» — danger-стиль (red/`--status-error`).
  - Меню позиционируется в пределах вьюпорта (не выходить за границы экрана).

### 3.4. Выбор иконки и цвета папки (починка «мёртвого» UI)
> Факт: раздел «Иконка и цвет» в `FolderModal` уже есть, но кнопки **не имеют `onClick`**, нет выбранного состояния, и значения не передаются в `createFolder`. Иконки/цвета реально применяются в Sidebar.

- **Где:** `FolderModal`.
- Требование: пользователь выбирает иконку (Lucide) и цвет; выбор сохраняется при создании/редактировании папки.
- Реализация:
  1. Добавить состояние `selectedIcon: string` (по умолчанию `'Folder'`) и `selectedColor: string` (по умолчанию `'#FF6B35'`).
  2. Навесить `onClick` на кнопки палитры иконок (список: `Folder, Code2, Megaphone, Zap, Sparkles, FileText` + опционально другие), визуально подсвечивать выбранную (`border-[var(--accent-primary)]`).
  3. Палитра цветов (8–10 цветов) — круглые кнопки с подсветкой выбранной.
  4. Передавать `icon` и `color` в `createFolder` (расширить сигнатуру стора: `createFolder(name, { parent?, icon?, color? })`).
  5. Починить `folderIcon()`: сейчас ищет иконку по `f.name` в массиве папок (ломается после переименования и при недетерминированном поиске). Передавать иконку напрямую из объекта `Folder` (или использовать стабильный id папки — см. §3.6).

### 3.5. Переименование папки (сделать доступным из UI)
> Факт: `renameFolder` реализован в сторе, но **не вызывается нигде в UI**.

- Требование: переименование папки доступно пользователю (пункт контекстного меню + хоткей `F2` на выделенной папке).
- Реализация: модал (или inline-поле в Sidebar) с вводом нового имени → `renameFolder`; обновить каскад родителя/детей (см. §3.1). После переименования корректно обновить `selectedFolder` и списки промптов.

### 3.6. Стабильный идентификатор папки (рекомендуется)
- Проблема: папка идентифицируется по `name`; переименование ломает `folderIcon()` по имени и ссылки. 
- Рекомендация: добавить `Folder.id: string` (UUID/slug), использовать его как ключ в последовательности; `name` оставить пользовательским. Миграция seed-папок.
- **Обратная совместимость:** при наличии старых данных без `id` — генерировать по имени при гидрации.

## 4. Доработка модели промпта

> Факт: `Prompt` = `{ id:number, title, tags[], preview, path, content, vars{}, starred, folder, createdAt, updatedAt, usageCount }`. В редакторе — **один textarea** (`content`) в трёх режимах (view/split/edit). Полей `system/context/output/useTemplate` нет.

### 4.1. Разделение на System / Context / Output (шаблонный режим)
- Требование: добавить опциональное разделение промпта на логические блоки (шаблонный режим):
  - `system` — инструкция для модели;
  - `context` — контекст/данные;
  - `output` — формат вывода.
- **Реализация (с миграцией, без потери обратной совместимости):**
  1. Расширить `Prompt`: `system?: string; context?: string; output?: string; useTemplate?: boolean`.
     - Если `useTemplate` не задан — считать обычный режим (используется `content`). Это сохраняет совместимость со старыми данными без этих полей.
  2. В редакторе добавить переключатель «Обычный» / «Шаблонный» (сегментированный контрол, как view/edit/split).
     - **Обычный:** существующий один `textarea` связан с `content` (без изменений).
     - **Шаблонный:** три раздельных текстовых поля (`system`/`context`/`output`) с заголовками «System Prompt», «Context», «Output format»; при этом нижняя панель переменных и счётчики действуют на **объединённый** шаблонный текст.
  3. **Объединение при копировании/экспорте/поиске/превью:**
     - ввести функцию-хелпер `getPromptText(p: Prompt): string`, возвращающую `content` в обычном режиме либо склейку `system + context + output` в шаблонном (с разделителями);
     - использовать её везде, где сейчас читается `prompt.content` (копирование, экспорт, `renderMarkdown`-превью, поиск, счётчики, `makePreview`).
  4. Обновить `seedPrompts`: добавить 1–2 примера с `useTemplate: true` и заполненными `system/context/output`.
  5. При миграции старых промптов (без новых полей) — `useTemplate: false`, поля пустые, работает как раньше.

### 4.2. Переменные `{{var}}` в шаблонном режиме
- Требование: `extractVariables()` и подстановка должны работать по **объединённому** тексту промпта (см. `getPromptText`), а поля ввода переменных в панели — маппиться на этот объединённый источник.
- Исправить дефект: `addVar` и `updateVar` идентичны и не чистят старые ключи при переименовании. Навести порядок: единый метод `setVar`, удалять неиспользуемые ключи (по расхождению с `extractVariables`).

### 4.3. Устойчивые id промптов
- Исправить коллизию `Date.now()`: использовать монотонный счётчик или `crypto.randomUUID()` для id. Сохранить тип `number | string` с миграцией старых числовых id (или унифицировать в `string`).

## 5. Доработка импорта/экспорта

> Факт: импорт выполняется через скрытый `<input type="file">` в `Sidebar` без модального окна и **без любого разрешения конфликтов** — промпты добавляются в начало массива с новыми id. Экспорт — в `ExportModal`, формат `.prmt` (JSON), **папки не экспортируются** (хотя в подсказке окна заявлено «Содержит метаданные, переменные и связи»).

### 5.1. Диалог объединения при импорте (.prmt/.json)
- Требование: при импорте из `.prmt`/`.json` показывать диалог «Объединение баз» с разрешением конфликтов по каждому промпту.
- **Признак конфликта:** совпадение пары `title` + `folder` (и, опционально, `content`).
- Действия на каждый конфликтный промпт (селектор в строке):
  1. **Пропустить** (`skip`) — не импортировать;
  2. **Переименовать** (`rename`) — добавить суффикс «(копия N)»;
  3. **Заменить** (`overwrite`) — заменить существующий (с сохранением `id`/счётчиков существующего);
  4. **Дублировать** (`duplicate`) — импортировать как новый, не трогая существующий.
- Не конфликтные промпты — добавляются как новые (по умолчанию «импортировать»).
- Массовые кнопки: «Все пропустить», «Все заменить», «Применить ко всем».
- Итог: `toast` с числом импортированных/пропущенных/заменённых.
- **Доработать импорт `.md`/`.txt`:** сейчас folder хардкодится в `'Development'`; предложить выбор папки (или импорт в текущую выбранную).

### 5.2. Добавить экспорт папок
- Требование: включить папки (и их иерархию: `parent`, `children`, `icon`, `color`, `order`) в `.prmt`-файл, и восстанавливать их при импорте (с созданием отсутствующих). Обновить `ExportData`-тип (сейчас не используется как аннотация — задействовать его).
- Обновить информационную подсказку в `ExportModal`, чтобы она соответствовала реальному содержимому.

### 5.3. Валидация импортируемых данных
- Обратная совместимость и устойчивость: проверять структуру импортируемого объекта (наличие `prompts`, валидные поля), игнорировать/обозначать некорректные записи, не «падать» целиком при битом файле. Выносить логику импорта/экспорта из `App.tsx` в `utils` (см. §10).

## 6. Electron-версия (перспектива, этап 2)

> Факт: **Electron в проекте отсутствует** (нет в `package.json`, нет main-процесса, нет preload). Веб-сборка — целевой дистрибутив. Этот раздел — **отдельный этап**, не должен блокировать этап 1 (веб-функциональность).

### 6.1. Глобальный хоткей Alt+Space
- Требование: глобальный хоткей `Alt+Space` открывает быстрый поиск поверх всех окон.
- Реализация (main-процесс Electron): `globalShortcut.register('Alt+Space', ...)`, показ/скрытие окна, отправка события `open-quick-search` через IPC.
- Renderer: подготовить слушатель `window.api?.onOpenQuickSearch(...)` через preload (без прямого доступа к `ipcRenderer` из UI — см. §6.4).
- **Совместимость:** в веб-сборке (без Electron) блокировать простыми опциональными элментами (`window.api` отсутствует — код работает, как сейчас).

### 6.2. Файловый вотчинг
- Требование: наблюдение за папками на диске и автообновление интерфейса при изменениях.
- Реализация (main-процесс): `fs.watch(paths, { recursive: true })` → событие → IPC → renderer обновляет список. Рекурсивно и с защитой от циклов.

### 6.3. Портативность данных (~/.promtova/data)
- Требование: в Electron-версии данные хранятся в файловой системе (`~/.promtova/data/*.json`), синхронизируются с состоянием (Zustand).
- Реализация: storage-адаптер Zustand, читающий/пишущий JSON-файлы через IPC (`main/storage.ts`); сохранение atomic (временный файл + rename), дебаунс.
- **Не смешивать с "Расположение данных" в Settings** для веб-версии (см. §8.3 — заглушка: для браузера кнопка «Открыть папку» невозможна без файлового доступа; следует либо убрать, либо показывать в зависимости от окружения).

### 6.4. Структура Electron (рекомендуемая)
```
electron/
  main.ts        — окно, globalShortcut, IPC
  preload.ts     — безопасный bridge (contextIsolation: true, contextBridge)
  storage.ts     — read/write данных
  fileSystem.ts  — watcher
package.json     — "main": "electron/main.cjs" (для ESM-сборки отдельный .cjs или сборка)
electron-builder.yml (или `build` в package.json)
```
- Безопасность: `contextIsolation: true`, `nodeIntegration: false`, только whitelisted IPC-каналы в preload.

> Факт: копирование **с** подстановкой (`handleCopy(true)`) не вызывается ни кнопкой, ни хоткеем. Есть только кнопка копирования **без** подстановки.

- Реализация:
  - обработчик `keydown`: `(e.metaKey || e.ctrlKey) && e.shiftKey && key.toLowerCase()==='c'` → `e.preventDefault(); handleCopy(true)`;
  - в шаблонном режиме использовать `getPromptText` (§4.1) с подстановкой `substituteVariables`.
- Обновить `ShortcutsModal`, чтобы заявленные хоткеи совпадали с реализованными (см. §8.1).

### 7.3. Кнопка «Переименовать» для промптов
